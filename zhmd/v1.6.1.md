# SpargeAttn 提速（v1.6.0 以来）— v1.6.1

本版本是 **v1.6.0 以来的 SpargeAttn 提速工作**。`spargeattn` 注意力后端
（基于 SageAttention2++ 内核构建的块稀疏注意力）此前在实际工作流中**比朴素的 SageAttention2 更慢**，
尽管它才是进化形态。以下四项改动消除了导致这一现象的固定开销，使 `spargeattn` 现在达到或超过
SageAttention2，同时保留其稀疏收益。

---

## 1. Sage2++ fp16 累加路径 + ragged 窗口修复

**提交：** `0185398` — *perf: fix ragged-window SpargeAttn path and use Sage2++ fp16 accumulate*

- **Ragged 窗口正确性：** 按组构建 `(n,H,L,D)` 张量时原用 `view()`，但 q/k/v 以
  `(total_seq,H,D)` 布局，且 NA 窗口化产生 **ragged（不等长）** 窗口，故 `view(_w,L,H,D)`
  抛出 *"shape is invalid for input of size …"*。现改用 `torch.stack`，并按窗口写回输出。
- **Sage2++ fp16 累加内核：** 当 `SAGE2PP_ENABLED` 开启且符号存在时，Stage-3 稀疏内核
  走 `qk_int8_sv_f8_accum_f16_…`（SageAttention2++ fp16 累加），否则回退 f32 累加。

实测（RTX 5060 Ti, sm120, bf16, H=24, D=128, 25×4032）：

| topk | spargeattn (Sage2++) | sageattn_2 | 加速 |
| --- | --- | --- | --- |
| 0.5 | 51.6 ms | 70.3 ms | **1.36x** |
| 0.25 | 42.6 ms | 71.0 ms | **1.67x** |

---

## 2. 等长窗口批处理（stock API、零拷贝）

**提交：** `8128ee6` — *perf: batch SpargeAttn per equal-length window group (stock API, zero-copy)*

stock 循环**每个 NA 窗口调用一次** `spas_sage2_attn_meansim_topk_cuda`。在实际工作流
（1080p，21 帧 → **每次 100 个窗口**，36 blocks × 2 attn）下，即**每步约 7200 次内核启动**，
而 `sageattn_varlen` 仅 72 次；WDDM 启动开销（约 0.15 ms）吞掉了稀疏收益，使 spargeattn
即便在低 topk 下也慢于 sageattn_2。

修正方案：按**相同长度**分组窗口，对批处理张量 `(n,H,L,D)` **每组调用一次 stock topk API**：

- 长度相同的窗口按背靠背排布（NA 惯例）时使用**零拷贝视图**；
- ragged 分组回退到 `torch.cat`。

API 及其内部的 block-map / LUT / quant / 稀疏内核**原生支持批处理**，因此这是**与 stock 完全相同的代码路径
—— 没有重新实现**。输出与逐窗口路径一致（ragged `99×2430 + 1×1000`：max_diff 1.5e-3，mean 4.4e-10）。

实测（RTX 5060 Ti, sm120, bf16, 100×2430）：

| topk | spargeattn（批处理） | sageattn_2 | 加速 |
| --- | --- | --- | --- |
| 0.5 | 101.0 ms | 111.9 ms | **1.11x** |
| 0.3 | 90.6 ms | 114.5 ms | **1.26x** |

> 曾先尝试批处理式的 *block-map 重新实现*，随后**已回退**（`879441b`）：由于
> `spas_sage2_attn_meansim_topk_cuda` 本就每次处理一个窗口并在内部使用 Sage2++ fp16 累加内核，
> 重新实现只会增加 `torch.stack` 拷贝并使 spargeattn 更慢。上述批处理保留 stock API，
> 仅改变调用粒度。

## 3. 去除每次调用的 D2H 同步

**提交：** `29a1d84` — *perf: eliminate per-call D2H syncs in SpargeAttn fast path*

零拷贝等长快速路径**每次注意力调用**都会执行 `(seq == seq[0]).all()` 加两次 `.item()` ——
即 **3 次 D2H 同步 × 每次 DiT forward 72 次调用 × 14 个 batch**。在 Windows/WDDM 下
每次同步忙碌等待约 3–7 ms，为每个 batch **增加数秒**，使 spargeattn 输给纯 SageAttention2
（**31s vs 29s**）。

修正方案：以 `(queue-shape, total-numel)` 为键**缓存一个 plan**：首次调用承担同步开销一次，
此后本次运行中的每次调用都走零拷贝快速路径且**无 D2H 同步**。过期 plan 不会误执行 ——
零拷贝 `.view()` 会用张量 numel 校验 `B*L`，不匹配时弹出 plan，回退到 ragged 路径。

## 4. 变长（varlen）委托给 SpargeAttn-hswq 库

**提交：** `3d93819`（`ef32a90` 恢复实测基线）— *delegate varlen handling to the library*

`call_sparge_attn_varlen` 现**委托给 fork 的 `spas_sage2_attn_meansim_topk_varlen_cuda`
（≥ 1.2.1）**，不再在调用端做分桶。该库在不违反内核定长前提的情况下同时支持两种布局：

- **等长**（所有窗口长度相同）→ 单次**零拷贝批处理启动**；
- **混合长度** → 在**库内**按相同 `(L_q, L_k)` 分桶；每个桶一次批处理启动。
  连续桶用零拷贝视图，分散桶用一次 gather + 一次 scatter。无逐序列启动，无 padding 浪费。
- 分桶 plan 以窗口长度的**无序多重集**为键缓存，故仅在调用间调换相同长度窗口的运行仍会命中。

**关于持久化缓存实验：** 曾加入实验性的持久化 Triton 缓存特性（默认 `TRITON_CACHE_DIR` +
`release_sparge_kernel_caches`），随后**已回退** —— 实测并未改变稳态速度，只让首次调用更慢。
spargeattn 路径保持**经实测确认的正确状态**（无持久化缓存计装）。

## 5. 变更集汇总（v1.6.0 → v1.6.1）

| 提交 | 变更 | 实测效果 |
| --- | --- | --- |
| `0185398` | Sage2++ fp16 累加 + ragged 修复 | 相对 SA2 最高 **1.67x** |
| `879441b` | 回退批处理式 block-map 重新实现 | 去除 stack 拷贝 |
| `8128ee6` | 等长窗口批处理（stock API、零拷贝） | 相对 SA2 **1.11–1.26x** |
| `29a1d84` | 去除每次调用的 D2H 同步 | 去除 3 次同步 × 每 batch 72 次调用 |
| `3d93819` | varlen 委托给库 ≥ 1.2.1 | 等长 1 次启动 / 混合分桶 |
| `ef32a90` | 恢复经实测确认的 spargeattn 基线 | — |

**最终结果：** 在实际工作流中，`spargeattn` 后端现与 SageAttention2 持平（或更快），
稀疏收益完好，快速路径无逐调用主机同步。
