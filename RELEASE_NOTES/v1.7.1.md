# SeedVR2 Video Upscaler — Release Notes (v1.7.1)

## Overview

SeedVR2 Video Upscaler v1.7.1 updates the **TensorRT RTX execution stack** to the current NVIDIA releases.

The previous stack pinned `tensorrt-rtx` to 1.6.1.120. This release moves the runtime to **1.7.1.116**, together with matching `onnx`, `onnxscript` and `polygraphy` updates. The installer is also corrected: it previously verified only whether a module could be imported, which meant the pinned versions in `requirements-windows-cu132.txt` were silently ignored whenever an older build was already present.

> **IMPORTANT — Existing TensorRT engines must be rebuilt.**
>
> TensorRT `.rtxplan` engines are bound to the TensorRT version that produced them. Engines serialized with `tensorrt-rtx` 1.6.1 **cannot be deserialized** by 1.7.1, and attempting to run them fails with:
>
> ```
> IRuntime::deserializeCudaEngine: Error Code 1: Serialization
> (Serialization assertion stdVersionRead == kSERIALIZATION_VERSION failed.
>  Version tag does not match. Note: Current Version: 100, Serialized Engine Version: 98)
> ```
>
> After upgrading, rebuild every engine in `tensorrt_backend/artifacts/` using the **`SeedVR2 Build TensorRT VAE Engines`** node (or `scripts/prepare_tensorrt.py`). Keep the existing engine files until the new ones have been verified, since the upgrade is not backwards compatible with previously serialized plans.

---

## 1. Dependency Updates

| Package | Previous | Updated |
|---|---|---|
| `tensorrt-rtx` | 1.6.1.120 | **1.7.1.116** |
| `onnx` | 1.22.0 | **1.23.2** |
| `onnxscript` | 0.7.1 | **0.7.2** |
| `polygraphy` | 0.53.4 | **0.53.6** |

`triton-windows` remains unpinned, so it continues to match the installed PyTorch build.

### 1.1 Why the TensorRT RTX upgrade forces an engine rebuild

TensorRT serializes engines together with an internal archive version tag. A runtime refuses to load a plan whose tag does not match its own, and there is no in-place migration path. The distinction between "engine exists on disk" and "engine is usable by the current runtime" therefore has to be handled explicitly:

- `find_engine_path()` in `src/core/trt_encoder.py` and `src/core/trt_decoder.py` resolves an engine purely by file name and size.
- Deserialization happens afterwards in `_engine()`; on version mismatch `deserialize_cuda_engine()` returns `None` and the loader raises `Could not deserialize TensorRT encoder/decoder: <path>`.

Because the file name still matches, the stale engine keeps being selected until it is either rebuilt or removed. A rebuild through the **`SeedVR2 Build TensorRT VAE Engines`** node overwrites the file in place and resolves the version mismatch.

## 2. Installer Correction (`install.py`)

### 2.1 The Problem

`ensure_package()` validated the environment by import alone:

```python
def ensure_package(import_name: str, install_name: str | None = None, no_deps: bool = True) -> None:
    try:
        __import__(import_name)
        return
    except ImportError:
        pass
    ...
```

Any importable version satisfied the check. When an older `tensorrt-rtx`, `onnx`, `onnxscript` or `polygraphy` was already installed, the pinned requirements were skipped without warning, leaving the runtime stack inconsistent with `requirements-windows-cu132.txt`.

### 2.2 The Fix

The pinned versions are now passed to `pip` explicitly:

```python
ensure_package("tensorrt_rtx", "tensorrt-rtx==1.7.1.116", no_deps=True)
# Linux: triton / Windows: triton-windows (no version pin; match installed torch)
ensure_package("triton", "triton-windows" if sys.platform.startswith("win") else "triton", no_deps=True)
ensure_package("onnx", "onnx==1.23.2", no_deps=True)
ensure_package("onnxscript", "onnxscript==0.7.2", no_deps=True)
ensure_package("polygraphy", "polygraphy==0.53.6", no_deps=True)
```

`requirements-windows-cu132.txt` carries the same pins, so a clean install and an in-place upgrade converge on identical versions.

## 3. Upgrade Procedure

1. **Update the node package** to v1.7.1 (Manager update, or `git pull` in the custom node directory).
2. **Install the new dependency stack**:
   ```
   pip install -r requirements-windows-cu132.txt
   ```
   or let `install.py` run on the next ComfyUI start.
3. **Rebuild the TensorRT VAE engines.** Run the **`SeedVR2 Build TensorRT VAE Engines`** node once per frame count / tile size combination you intend to use. Engines built with 1.6.1 are unusable on 1.7.1.
4. **Verify** that the rebuilt plans deserialize before starting production work. A version mismatch surfaces immediately at Phase 1 as `Could not deserialize TensorRT encoder`.

> **Note on engine scope:** only the frame counts and tile sizes you actually rebuild will be usable. If `engine_tile` is left on `auto`, the loader prefers the largest available tile on disk (1024 → 768 → 512 → 256), so a stale large-tile engine left behind will still be selected ahead of a freshly rebuilt smaller one. Pin `engine_tile` explicitly, or delete the outdated plans, while the rebuild is in progress.

---

## 4. Compatibility

- No changes to node inputs, outputs, or workflow JSON. Existing workflows load unchanged.
- No changes to `src/` outside the dependency pins and installer.
- Engines serialized by this release require `tensorrt-rtx` 1.7.1 or newer; they cannot be read by 1.6.1.
